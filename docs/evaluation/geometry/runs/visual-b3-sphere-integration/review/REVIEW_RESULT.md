## Findings

### BLOCKER

### IMPORTANT

**I-1. A `/2` plane target with more than three points is silently cut to three, so a non-coplanar target is served.**
- Where: `typed_fact_next_bridge.py:83-86` accepts `len(plane) >= 3`. `planner.py:1021` then emits
  `{"plane": b[:3]}`. `engine.kiem_mat_viet` (`engine.py:759-761`) checks only the call's plane, which is already cut,
  so the dropped labels are never checked.
- The engine's own comment at 758 says extra labels "must also be in the same plane". The angle functions keep them;
  this distance path loses them before the engine sees them.
- Scenario (probe 2b): the quote reads "(ABC)" and the target plane is `["A","B","C","A'"]`. These four points are not
  coplanar, but the route returns SERVED 144. The provenance shows `plane: ["A","B","C"]`, so the extractor's bad
  target leaves no trace.
- The answer still matches the source, because `_cung_mat` ties the three kept labels to the quoted plane. But the
  bridge docstring says "anything else is refused, never guessed", and this violates it.
- It also diverges from `/3`: `adapter3_simulation.py:1138` passes the full list to `AskDistancePointPlaneArgs`, whose
  `plane` has `max_length=3`, so `/3` refuses it. The report says the slice adopts the `/3` contract "verbatim"; on
  arity it does not.
- The same cut causes over-refusal (probe 1b): the valid plane "(AMBC')", with M the midpoint of AB, is refused
  `SOURCE_OBJECT_MISMATCH` because the first three labels A, M, B are collinear.
- Fix in one place: the planner should keep the full list for the engine's coplanarity check, or the bridge should
  refuse a target whose label set is not exactly the quoted plane.

**I-2. A stated "skew" relation that is false is not checked; the route serves instead of refusing as inconsistent.**
- Where: the `ask_distance_lines` source pattern (`registry.py:2829-2831`) lets "chéo nhau" through as optional
  wording. Nothing checks it against the built figure.
- Scenario (probe 6j): "Tính khoảng cách giữa hai đường thẳng chéo nhau AB và AC." returns SERVED d = 0, although AB
  and AC meet at A.
- Scenario (probe 6k): "chéo nhau AA' và BB'" returns SERVED d² = 36, although the lines are parallel.
- AGENTS §3 says contradictory data must be refused (`inconsistent`), not answered. The weakness is in the shared
  Source Gate and predates B3, but B3 is what makes it reachable on `/4`.

**I-3. The role-aware oracle checks hue families, not the policy colours, and tolerates a second cobalt-highlighted
section.** Details are in the verdict section below.
- Synthetic fill #FB923C (causal-tier orange) with boundary #0075DE (the generic `dich` blue) passes
  (`probe_role_oracle3.mjs`).
- A second section with a full cobalt boundary passes as long as its perimeter is up to about 40 % of the target's
  (`probe_role_oracle2.mjs`: share 0.835 / 0.771 / 0.715, all at or above 0.7).

**I-4. The browser probe classifies front and hidden edges using an eye position in the wrong frame whenever a display
rotation or chart metric is present.**
- Where: `section-role-browser-probe.mjs:107` passes `cam.position`, which is in world coordinates, to
  `sectionBoundaryWorld`. That function works in payload coordinates.
- The snapshot's view matrix is already view × model when `coXoay` is set (`scene3d-view.tsx:3009-3021`), so the
  projection is right. But the hidden/front decision uses `dot(n, eye - mid)` with an eye that has not been taken back
  through `model_matrix_column_major`.
- Scenario: a section on a pyramid with a tilted base (`quayHienThi` not the identity) or any scene with a
  `chart_metric`. Edges are misflagged, so front edges get the lenient aggregate threshold of 0.4, or dashed hidden
  edges get the strict per-edge 0.75. The first wrongly passes a missing front arc; the second wrongly fails.
- The three probe cases may be unrotated, so the baseline would not show this.

**I-5. Cone sections get the wrong hidden flags.**
- Where: `section-role-oracle.mjs:195-198` treats cones like cylinders and uses the radial direction from the axis as
  the surface normal. A cone's lateral normal is tilted by R/h.
- Probe I in `probe_role_oracle.mjs`: a cone with R = 2, h = 4, a circle section at z = 2 and the eye at (3, 0, 9).
  20 of 32 segments are flagged hidden, and 14 of 32 disagree with true surface visibility.
- `geometry-samples.json` contains cone solids, so this case can occur.

### MINOR

- **M-1.** A degenerate segment target `{segment: ["A","A"]}` with the quote "độ dài đoạn thẳng AA" is SERVED 0
  (probe 4i). Nothing in the bridge, planner or `Seg` type requires two distinct endpoints.
- **M-2.** A degenerate line `["A","A"]` (probe 3h) is refused, but with `ENGINE_EXECUTION_FAILED` (`GeometryError
  DEGENERATE_POINTS`). `hybrid_compiler_benchmark.py:442` classes that code as `system`, so an input fault is counted as
  a system fault. The planner already has `DEGENERATE_LINE`, but only for `plane_relation`.
- **M-3.** Coincident or intersecting lines return d = 0 (probes 3c–3e). This is mathematically correct. The registry
  describes `ask_distance_lines` as "(chéo nhau)", so the wording should match the behaviour (see I-2).
- **M-4.** Hover paints exactly like selection: `o.id === hoveredSection ? "dich"` at `scene3d-view.tsx:3450`, plus the
  `netMien` cobalt. Hovering a second section while one is selected shows two cobalt boundaries, which contradicts
  "only the selected boundary turns cobalt".
- **M-5.** `hoveredSection` is not reset when the scene changes. If a new scene reuses the id (for example a section
  "T"), it shows as hovered until the pointer moves or leaves.
- **M-6.** Each hover enter or leave rebuilds every object, because `hoveredSection` is in the deps of the build
  effect. Also, `netMien` turns the boundary cobalt whenever `noiBat === true` (the step-playback highlight), not only on
  selection. It is unclear whether that is intended; the hex `0x2563eb` is hard-coded rather than taken from the
  palette.
- **M-7.** Ellipse fix (`scene3d-view.tsx:1695`): `n = M × m` is correct; `tt × n` points outward for either sign of
  the payload normal. If `major_dir ∥ minor_dir` (degenerate), `n` becomes the zero vector and the band silently
  vanishes instead of failing. The circle branch is unaffected because it builds in local xy and applies a proper
  rotation.
- **M-8.** `oracle_scalar_radius.py` checks only that the scene is internally consistent with its own GIVEN quantity
  value. A scene where R = 6 everywhere (radius_sq 36, circle 27, r = 3√3, S = 27π) is VERIFIED
  (`probe_sphere_layer.py`). Fidelity to the source "bán kính 5" is covered only by
  `test_given_radius_is_the_source_number`. This is acceptable, but the docstring's "checks such a sphere against the
  GIVEN radius" should say "the GIVEN radius as carried in the scene".
- **M-9.** The `main.py` CACHE_VERSION comment says "Row v128 THẬT … vẫn HIT", which reads as if the stale row still
  hits after the bump. `decision.json` and the migration test say the opposite: it would hit without a bump and must
  MISS after it.
- **M-10.** `b3-distance-browser-e2e.mjs:136`: `witness_rendered` passes trivially when no tied witness is provided.
  It is reported, not failed. Also, `no_internal_name` uses `\b` with `/u`, which in JavaScript is ASCII-only around
  Vietnamese letters.
- **M-11.** The circle case in `f2-role-aware-oracle/inputs/cases.json` picks `samples.6.envelope` by array position.
  After sphere-src merges, sample 6 is still `cau-cat-mat-phang` and S, C and I still exist (checked). But the scene
  changes: plane (P) is no longer hidden, and points A, H, U, W are gone. Any browser baseline taken on b3-dist must be
  measured again after the merge.

## May the role-aware oracle replace the hue gate for section targets?

**Not yet.** The design is right: it scores each object along the projected boundary of the selected section, and it
checks fill and blue ownership separately. That is a real improvement over the hue-only gate, which fails the
policy-compliant frame by construction. The synthetic faults it targets (terracotta rim, magenta rim, one missing edge,
grey or cobalt fill, a large foreign blue area) are caught.

These wrong renderings still pass, all observed on synthetic frames:
1. Wrong colours of the right family. The `xanh`/`cam` bands do not separate cobalt #2563EB from the generic
   target-tier blue #0075DE, or terracotta #C85A32 from causal-tier orange #FB923C / #C2410C. A rim drawn in #0075DE
   with a fill in #FB923C passes. A colour-distance check (ΔE to the policy hex), not hue membership, is needed for the
   rim and the fill.
2. Another section highlighted too. A full second cobalt boundary with up to about 40 % of the target's perimeter
   passes the 0.7 ownership share. Inject a "highlight a non-selected section" fault on a scene with two or more
   sections, and use a stricter or per-object ownership rule.
3. Partial loss. A 25 % gap in one front edge passes (coverage 0.75 ≥ 0.75). Front edges dashed at 50 % pass. Up to
   half the boundary length can be unscored (under overlays) and never drawn, and still pass.
4. Frame and geometry bugs in the hidden classification. The eye is in the wrong frame for rotated or chart-metric
   scenes (I-4), and cone normals are wrong (I-5). Either can move a front edge onto the lenient 0.4 threshold.
5. Evidence. No Chrome receipt for `section-role-browser-probe.mjs` is committed at cb8d7c4a or 6c1befcd: the
   `f2-role-aware-oracle` run holds only `inputs/`. The fault probe has no "wrong section highlighted" fault, its
   `wrong_object` fault is caught by the DOM identity check rather than by pixels, and it must be measured again after
   the sphere-src merge (M-11).

Conditions to say yes: fix 1–4, add the missing faults, commit a browser receipt in which the baseline passes and every
fault is detected, at desktop and mobile, on at least one rotated scene and one multi-section scene.
